# 0050 — App language: Portuguese and English

- **Status:** accepted
- **Date:** 2026-11-13

## Context

Block 4.2.6: the desktop app was written in Portuguese, with every text inline in the components.
The beta has people abroad, and the spec asks for Portuguese (Brazil) and English, the system's
language by default (Portuguese when the system's has no translation), dates and numbers in the
language's format, and a switch that applies right away. Texts that come from the API and e-mails
stay in Portuguese for now. The block was moved ahead of 4.2.3–4.2.5 so the new screens are born
translated instead of being extracted later.

## Decision

**Library.** `i18next` + `react-i18next` (both MIT), pinned. Mature, with plurals (`_one`/`_other`
through `Intl.PluralRules`), interpolation, `<Trans>` for text with markup inside, and an instance
that also runs in the main process. Lingui (needs a compile step) and react-intl (heavier) were
considered; a hand-rolled `t()` would have to reimplement plurals and markup.

**Files.** `src/shared/i18n/locales/<lang>/<area>.json`, one file per area (`common`, `auth`,
`chat`, `call`, `settings`, `addons`...). pt-BR is the source. All areas go in one namespace, so
keys read `area.thing` (`t('chat.composer.placeholder')`). `resources.ts` imports every file; the
English object is typed as the Portuguese one, so a missing key fails `tsc`, and keys passed to
`t()` are checked against pt-BR (`i18next.d.ts`). `resources.test.ts` checks that English has no
extra keys, keeps every `{{variable}}` and `<tag>`, and that no text is empty.

**Choosing the language.** `language: 'system' | 'pt-BR' | 'en'` in `settings.json`, on this
computer (not synced with the account: the sign-in screen needs it before anyone signs in, and the
system language is per computer). `system` reads `app.getPreferredSystemLanguages()` once and takes
the first language with a translation (`pt-*` → pt-BR, `en-*` → en), else pt-BR. The preload asks
the main process synchronously (`ipcRenderer.sendSync('i18n:get')`), so the first render is already
in the right language. Configurações › Idioma offers "Seguir o sistema (…)", "Português (Brasil)"
and "English".

**Switching without restarting.** `App` calls `useTranslation()`, so a language change re-renders
the whole tree (no component is memoized). That makes the module-level `t()` from `lib/i18n` safe
anywhere during render, which is what most components use; it must never run at a module's top
level. Lists defined at module level (permissions, statuses, tips, tour steps, addon names) expose
`label`/`title`/`text` as getters, so callers read them unchanged and always get the current
language. The detached call window and the overlay widgets render through portals from the same
tree, so they follow too. Settings › Idioma saves the choice and the main process switches its
own texts and rebuilds the tray and the Mac menu.

**Main process.** Its own i18next instance (`main/i18n.ts`, no Electron import, so it can be
tested) for the tray, the Mac menu, the "still running" notice, the loading screen's status and
the overlay's shortcut errors and flashes.

**Formatting.** `lib/format.ts`: `dateFormat(options)`, `numberFormat(options)` and `graphemes()`,
cached per language and options. The old module-level `Intl.DateTimeFormat('pt-BR', …)` constants
became option objects. The emoji catalog (names, groups, search) loads per language from
emojibase-data's `pt` or `en` files. Excalidraw gets `langCode` from the app's language.

**API texts.** Account errors the app already mapped from the API's English details are
translated. Server type names and descriptions are translated by type, with the API's text as the
fallback. Everything else the API writes (badge names and how to get them, the official account's
messages, server-side 503 notices) and the CHANGELOG shown in "Novidades" stay in Portuguese.

**No fixed text left.** `test/hardcodedText.test.ts` parses the renderer with the TypeScript
compiler and flags text written straight in JSX, string props that are shown (`label`, `title`,
`aria-label`, `placeholder`...), strings given to `setError`/`toast`/…, templates in shown props,
and any string with Portuguese letters. Brands and examples are allowed by name, with the reason.
`HARDCODED_TEXT_OUT=<file>` writes the full list.

## Consequences

- Every new screen uses keys from its first commit, in both files; the tests fail otherwise.
- Translating the API's texts (badges, notices) later means sending codes or keys from the API.
- English copy was written during the extraction; it's worth a read-through by someone fluent.
- A third language is a folder of JSON files plus one line in `LOCALES` and `systemLocale`.
